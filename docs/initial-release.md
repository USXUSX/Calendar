# Goal 1 初期リリース仕様

Issue #86と[us承認判断](https://github.com/USXUSX/Calendar/issues/86#issuecomment-5555665017)に基づく仕様。機能実装済みという意味ではない。現在地は[ロードマップ](development-roadmap.md)、既存の正本・更新境界は[Baseline](calendar-baseline.md)と[表示・更新契約](trip-detail-model.md)を参照する。

## 1. 初期リリースの完成範囲

Chatで完成に近い旅程を作り、CALで取込・表示・手動編集・候補追加・情報補完・天気等の細部を仕上げる。操作中の予定以外を自動変更しない。

| 機能 | Goal 1の完成条件・境界 |
| --- | --- |
| 基本表示・手動編集 | iPad mini / iPadで旅程を閲覧し、具体値を編集できる |
| 日別代表エリア | 日付行で「小樽→札幌」等を設定・表示する。個々の予定にエリア属性を追加しない |
| Chat貼付 | 下記形式から新規Tripを複数日まとめて登録する。既存Tripへの追記・置換・差分更新は対象外 |
| ① 時刻矛盾 | 明白な時刻矛盾だけを赤字等で明示する。他予定の時刻を自動変更しない |
| ② 条件指定の予定追加 | 1回1件、条件に概ね合う予定を追加する。取得できなければ候補なしを許容する |
| ③ 店・観光地候補追加 | Issue #92に従い、AFM最大3推薦から0〜3件を対象予定の候補へ追加し、元条件を保持する。1件でも正式な場所は変更しない。難しいランキング条件は対象外 |
| ⑤ コメント補完 | 「概要」「営業日」「見どころ」等の指定条件で、根拠のある情報を既存コメントへ追記する |
| ⑥ URL・座標等の補完 | 施設同定と保存可能な情報の補完を共通基盤とする。一定の作り込みを許容し、全件成功は要求しない |
| ⑦ 天気 | 座標・対象日が対応する予報期間内だけ扱い、遠い旅行は予報対象外とする |

④移動時間込みの整合性確認、固定予約保護、OpenAI APIによる旅程生成・再生成はGoal 1に含めない。地図画面、メール取込、Chat API連携も対象外。既存OpenAI経路は削除・改修せず保持し、その完成や追加検証を初期リリースの完成条件にしない。AFMの採用・実装・実測は本仕様で決定しない。

①は明示された時刻と順序から判断できる矛盾を扱う。未定時刻や行動順序が曖昧な場合は無理に判定せず、移動所要時間の推測・経路照会・予定の自動繰下げへ拡張しない。②③⑤⑥⑦でも、取得結果を理由に他予定を変更しない。

## 2. Chat→CAL貼付形式

### 項目とまとまり

日本語ラベル付きのテキストとする。厳密なJSON、CAL内部ID、Schema全文をChatへ渡すことを前提にしない。1回の入力は1つの新規Tripで、`日付`から次の`日付`までが1日、`予定`または`移動`から次の予定・移動・日付までが1項目である。記載順をその日の順序として扱う。

| ラベル | 標準出力と解釈 |
| --- | --- |
| `旅行名` | Tripの名称。入力全体の先頭に1回 |
| `日付` | `YYYY-MM-DD`。複数日はこの見出しを繰り返す |
| `代表エリア` | 直前の日付に属する自由文。経由地一覧や経路計算への指示にはしない |
| `予定` | `開始～終了 \| 内容`。時刻未定なら`未定 \| 内容`、開始だけ分かるなら`09:00 \| 内容` |
| `カテゴリ` | 直前の予定についてChatが`観光`・`食事`・`宿泊`のいずれかを1回出力する。移動には付けない。CALは貼付値を解釈・Validationし、自動推測しない |
| `場所` | 直前の予定の場所名。住所や座標がなくてもよい |
| `移動` | `開始～終了 \| 出発地→到着地 \| 手段`。同じ移動を予定として重複記載しない |
| `コメント` | 直前項目の通常コメント。予約保護やAIへの実行命令にはしない |
| `候補` | 直前の予定に対する候補場所名。複数候補は行を繰り返す。訪問確定や別予定と解釈しない |
| `URL`・`住所`・`座標` | 直前の場所または候補の任意情報。座標は緯度, 経度。分からなければ省略する |

旅行名、日付、代表エリア、時刻・内容・カテゴリ・場所を基本項目としてChatへ求めるが、欠損だけで貼付全体を拒否しない。コメント、候補、URL、住所、座標は任意。移動の出発地・到着地のどちらに付くか不明な補足は、勝手に割り当てず未解釈として確認する。

### 複数日Tripの入力例（合成例、時刻は例示）

```text
旅行名: 北海道旅行
日付: 2027-06-12
代表エリア: 小樽→札幌

予定: 09:00～10:00 | 小樽運河を散策
カテゴリ: 観光
場所: 小樽運河
コメント: 朝の景色を楽しむ

移動: 10:30～11:15 | 小樽駅→札幌駅 | 鉄道

予定: 12:00～13:00 | 昼食
カテゴリ: 食事
場所: 未定
候補: サンプル食堂A
住所: 札幌市内（例示）
URL: https://example.com/restaurant-a
候補: サンプル食堂B
コメント: 当日の気分で候補から選ぶ

日付: 2027-06-13
代表エリア: 札幌

予定: 09:00 | 公園を散歩
カテゴリ: 観光
場所: 大通公園
コメント: 終了時刻は未定

予定: 未定 | お土産を買う
カテゴリ: 観光
場所: 札幌駅
```

Chatへの短い指示例：

> この旅行をCAL貼付用の日本語ラベル付きテキストで出力してください。旅行名を先頭に置き、各日を日付と代表エリアで区切り、予定または移動を順番に並べてください。予定は時刻・内容・場所を記載し、予定ごとに「カテゴリ: 観光」「カテゴリ: 食事」「カテゴリ: 宿泊」のいずれかを必ず1行付けてください。移動は時刻・出発地→到着地・手段を記載し、カテゴリは付けないでください。コメント、候補、URL、住所、座標は分かる範囲だけ付け、不明値は省略または未定にしてください。候補を訪問予定に変えたり、URL・座標を創作したりしないでください。JSONやCAL内部IDは不要です。

### ベストエフォート解釈と登録

- 前後空白、空行、全角・半角のコロンや数字、`9:00 / 09:00`、時刻区切りの`～ / 〜 / -`等の軽い表記揺れを吸収する。Markdownのコード囲みも入力内容と分離する。任意の自由文を完全に解釈する保証はしない。
- `未定`、空欄、省略は不明値として扱う。終了時刻、場所、座標、URLを推測で補わない。日付に年がない等、一意に解釈できない値は確認対象とする。日跨ぎや時差も時刻だけから推測しない。
- 解釈結果を日別・予定別に示し、未解釈箇所と不足・曖昧な値を確認・補正して登録する。読めなかった行を黙って捨てない。形式上必要な旅行名・日付・予定内容等の不足はここで補正する。
- カテゴリはChatが予定ごとに出力した`観光 / 食事 / 宿泊`をCALが既存の`sightseeing / food / accommodation`へ対応付けてValidationする。CALは予定内容や場所から推測・上書きしない。有効な値はそのまま使い、不正または欠損時だけカテゴリの補正確認へ返す。
- 登録は新規Tripの一括登録だけとする。同名旅行や似た予定を既存Tripへの更新指示と解釈せず、既存TripとそのIDを変更しない。候補の同名だけで施設の同一性を断定しない。
- 採用する名称・日付・順序・日別代表エリア・予定・カテゴリ・移動・コメント・候補・保存可能な地点情報をCALへ渡す。入力全文やChat会話履歴を旅程の別正本にしない。登録前の貼付原文は確認用であり、恒久履歴を新設しない。
- CALがstable IDと参照を構築し、内部の完全Trip表現を必要なSchema / semantic Validationへ通して初回採用する。貼付の寛容な解釈と正本採用のValidationを混同しない。未補完値は既存契約で許される不明値として扱い、表現できない内容は確認・補正へ返す。
- UIはCALの意味境界を使い、直接SQLiteやTrip JSONを書き込まない。既存のWorking export → complete candidateの手動往復は別経路として保持する。

日別代表エリアは既存の`Day.routeSummary`と日見出しの`route_summary`を再利用する方針とし、日主題`Day.title`や各予定の属性へ複製しない。これは自由文表示・検索hintであり、天気座標や移動経路を確定する値ではない。新規取込のcommand形状、未定項目と現行Schemaの具体的対応、初回採用の書込み処理は後続実装Issueで契約化し、本IssueではSchemaを変更しない。

## 3. 外部データの取得・保持

### 共用する最小能力

| 能力 | 主な利用機能 | 入力と結果 |
| --- | --- | --- |
| 施設検索・同定 | ②③⑥ | 名前、日別代表エリア、既知の住所等から少数候補を取得。名称・住所・位置等で照合する |
| 地点情報・根拠情報取得 | ⑤⑥ | 同定した施設のURL・住所・座標、概要・営業日等の根拠を取得。既存Place enrichment境界へ保存可能な候補だけ渡す |
| 天気取得 | ⑦ | 確認できた地点座標と現地日付に対応する予報を取得。取得時刻・対象日・単位・出典を伴う |

②③⑤⑥は施設同定と取得adapterを共用し、⑦は利用可能な同じ地点座標を使う。代表エリアが「小樽→札幌」でも中間座標や予報地点を勝手に作らない。地点不明なら天気は未取得とし、予報期間外と取得失敗も区別する。

adapterに認証、利用上限、timeout、取得先ID、出典、取得時刻、保存・表示条件、有効期限を閉じ込める。CALは対象identity・型・値・参照と採用を担当し、画面は意味境界の結果を表示する。機能ごとに同じ施設の取得処理を重複実装せず、ENTへの蓄積、TSK Job、新しい常駐サービスを前提にしない。

検索結果が複数でも追加は1回1件。同名施設・支店等が曖昧なら未確定候補として扱い、既存の非空値を暗黙に上書きしない。候補なし、曖昧、取得不能、未補完は元の予定の保存・表示を阻害しない。外部照会は施設名・地域や必要な座標・日付に限定し、Trip全文や参加者・予約情報を送らない。取得本文にある命令を実行せず、最新情報をAIの記憶から補わない。

### 正本と一時情報の境界

| 情報 | 扱い |
| --- | --- |
| 採用した予定・日別代表エリア・候補 | CALの旅程正本。外部検索結果そのものとは区別する |
| 独立した手入力、保存可能と確認した地点の名称・住所・座標・URL | 採用した値をformal Place等の既存正本へ収束させる。地図用の別正本を作らない |
| 根拠に基づくコメント追記 | 保存可能な範囲の短い情報を出典とともに採用する。取得本文全体をコメントへ転載しない。営業日等は取得時点の情報であり将来の保証ではない |
| 未採用の検索結果・取得本文・provider固有メタデータ | 一時取得。許可された範囲だけcacheし、利用条件・有効期限に従い破棄・再取得する |
| 天気 | 更新可能な一時Context / cache。formal Tripへ恒久保存しない。取得時刻と予報対象を表示し、期限切れを最新予報として扱わない |

保存許諾が不明なfieldを正本への採用payloadに混ぜない。ユーザーが候補を選択してもproviderの保存制限は解除されない。出典表示義務は一時表示にも適用し、要約やコピーを経由して制限を回避しない。provider横断の一律TTLや永久保存を定めず、各adapterで許諾と用途に基づく期限を設定する。cache・取得先ID等をTrip schemaへ追加しない。実データ・cacheの配置はローカル専用とし、Git / Calendar_GDへ入れない。

### Goal 1の候補データ源方針

2026-09-06時点の公式資料を根拠とする。これは採用候補と優先順位の決定であり、契約締結、API有効化、課金、live実証の許可ではない。

- **永続補完**：保存可能な公開データを優先し、[Wikidataの構造化データ](https://www.wikidata.org/wiki/Wikidata:Data_access)を候補とする（CC0）。公式サイト等は掲載されているだけで自由な取得・転載が許されるとはせず、取得・保存可能な情報に限定する。Wikidataだけで飲食店網羅や最新営業情報を満たすとは想定せず、見つからない情報は手入力・未補完を許容する。
- **制限のある施設検索サービス**：[Google Places](https://developers.google.com/maps/documentation/places/web-service/policies)等の値を一律にformal Tripへ永久コピーしない。Googleのplace ID保存例外を他fieldへ広げない。Apple Mapsや飲食店API等を追加候補にする場合も、検索品質だけでなく必要fieldの保存・表示条件を後続Issueで確認してから接続する。Goal 2の地図providerを暗黙に決めない。
- **天気**：[Open-Meteo](https://open-meteo.com/en/docs)を第一候補とする。APIの予報範囲内（既定7日、最大16日）だけ取得し、それより先は予報対象外とする。[非商用利用条件とCC BY 4.0](https://open-meteo.com/en/terms)に従い出典を表示する。無料枠の利用上限・稼働保証のない条件もadapter設計時に確認する。
- 食べログ点数順等の網羅的ランキング取得、自動スクレイピングを必須能力にしない。人が入力した参照リンクは自動取得基盤と切り分ける。

## 4. 後続実装の小さな単位

次は分割候補であり、本Issueから実装や他repo変更を開始する許可ではない。各Issueで対象repo、既存実装との差分、最小Validation、必要なus確認を定める。

1. **日見出しと手動編集**：代表エリアの意味境界と表示・編集を接続し、基本表示・編集の具体的な支障を直す。
2. **新規Trip貼付**：上記2日例、時刻・地点の欠損、軽い表記揺れ、未解釈行を確認・補正して一括登録する。既存Trip不変と不正な正本の非採用を確認する。
3. **共通施設取得・⑥補完**：代表施設で同定品質と保存可能fieldを確認し、adapterから既存Place境界へ接続する。曖昧・失敗・未補完を扱う。
4. **②予定追加／③候補追加**：共通取得結果から各1件の追加を別々の小さなIssueで接続し、他予定の不変と重複候補の扱いを確認する。
5. **⑤コメント追記**：根拠と出典を伴う追記を対象予定だけに適用し、既存コメントを保持する。
6. **①明白な時刻矛盾**：時刻変更時の限定検出と表示を実装し、他予定が自動変更されないことを確認する。
7. **⑦天気**：地点・日付の対応、予報期間内／外、失敗、cache期限、出典表示を接続する。

各機能の実装・最小Validation後に、対象端末で取込から細部仕上げまでの実用性を確認して初期リリースを判断する。既存の合成demoやOpenAI経路のValidationだけで、この完成を代替しない。
